# Fabric network and lifecycle

## Supported application topology

The application trusts `Org1MSP` and `Org2MSP`, channel `aegis`, chaincode `aegis`. Each organization controls its CA, TLS CA, MSP definitions and peer administration. Fabric Gateway 1.13.0 is pinned separately from Fabric contract/shim 2.5 dependencies. The CA bridge uses the official Fabric CA 1.5.22 CLI rather than the deprecated Node CA SDK. See official [Gateway APIs](https://hyperledger.github.io/fabric-gateway/main/api/node/) and [CA registration/enrollment guide](https://hyperledger-fabric-ca.readthedocs.io/en/latest/users-guide.html).

CouchDB is the peer state database; the application uses explicit ledger keys and history queries rather than unbounded rich queries. Composite audit and operation keys support deterministic lookups. Fabric state is authoritative; PostgreSQL does not replace it when a peer fails.

## Reproducible development channel

Install Docker/Compose and official fabric-samples plus matching binaries/images. A verified Fabric 2.5 release and CA 1.5.22 are appropriate starting points; validate organizational compatibility before upgrades. Follow the official [installation guide](https://hyperledger-fabric.readthedocs.io/en/latest/install.html). This repository does not download or execute an unpinned remote installer.

```bash
export FABRIC_SAMPLES_DIR=/absolute/path/fabric-samples
bash scripts/fabric-deploy.sh
```

The script builds chaincode, creates `aegis` with CAs/CouchDB and deploys with `AND('Org1MSP.peer','Org2MSP.peer')`. It supplies `chaincode/collections.json`, with both MSPs, member-only read/write, explicit bilateral endorsement and no automatic block purge. The collection is provisioned for confidential commitments; current essential workflows use shared-channel cryptographic commitments and private S3 objects. No raw PII or documents are written into it.

The official test-network is a **development** network: a single orderer, example organizations and a peer Docker-socket dependency. Do not expose it publicly or describe it as an HA production network. The production application Compose file intentionally does not mount a Docker socket.

## CA registration and enrollment

A registrar has least-privilege `hf.Registrar.Roles=client`, an appropriate affiliation and allowed attribute names. Registration must be performed by the organization, not a browser selecting a role. `scripts/fabric-register.sh` registers a client with a single-use enrollment secret and CA-issued `aegis.did` certificate attribute. Redirect its secret output to a restricted handoff file; never enable shell tracing. Organization revocation automation additionally needs `hf.Revoker` and `hf.GenCRL`; keep its MSP keys in the restricted bridge mount.

The first administrator requires CA-issued `aegis.bootstrap=true:ecert` **and** its exact `aegis.did` attribute. Register this exceptional attribute using the registrar only. Call `/api/auth/enroll`, save the one-time downloaded PKCS#8 key securely, then bootstrap through the internal bridge using an operator-controlled HTTPS client:

```bash
# BRIDGE_TOKEN is a secret environment variable, never committed.
curl --cacert /secure/ca.crt https://BRIDGE_HOST:8443/bootstrap \
 -H "Authorization: Bearer $BRIDGE_TOKEN" -H 'Content-Type: application/json' \
 -d '{"actor":"did:aegis:YOUR_ORG_ADMIN"}'
```

Each MSP may bootstrap only once. New normal users enroll first; an administrator creates their identity using the exact certificate SHA-256 returned by enrollment. The CA extension and certificate hash must both match. Have a user propose their own Manager/Admin role and a different administrator approve it. Establish at least two organization administrators before handing over operations; the application intentionally has no unaudited lost-admin bypass.

Enrollment keys are generated by the CA CLI, converted to PKCS#8, returned once over TLS and retained in the bridge AES-GCM wallet for per-user signing. The CLI receives enrollment secrets in a captured child environment, not argv or central logs. Temporary directories are removed. This is a custodial signing model; see SECURITY.md.

## Contracts and authorization

`Operations` dispatches validated commands, ledger operation deduplication, snapshots, governance, recovery and organization configuration. IdentityRegistry, CredentialRegistry, AssetRegistry, OwnershipTransfer and AuditRegistry independently enforce domain rules. RolePolicyRegistry exposes the fixed supported permission matrix. Only active enrolled callers whose MSP, DID and certificate digest match the ledger can invoke protected methods. `_event` is an internal helper excluded by Fabric metadata discovery.

On-chain transfer state includes requester, recipient organization, acceptance, separate approver and a policy-captured transaction-timestamp expiry (15 minutes by default; versioned changes require independent Admin approval). Foreign allocation is rejected. Cross-organization transfers are deliberate: destination acceptance plus independent source approval moves the owner and asset organization. Both peers endorse the chaincode transaction. Recipient identity activity, current owner activity and final approver role are checked before finalization.

## Submission, commit and events

The bridge endorses a proposal, returns serialized transaction bytes and transaction ID, and submits only after the worker persists them. It reconstructs commit-status requests with the official SDK. A network timeout is not proof of failure; the same bytes/ID are retried and committed events reconcile ambiguity. No simulated transaction ID or SQLite fallback exists in production.

The event reader uses authenticated Gateway chaincode events with block **and transaction** checkpoints. Deduplication, projection and checkpoint updates occur in one PostgreSQL transaction. Do not advance a checkpoint without a successful projection. The audit/event identity must be enrolled, bootstrapped or role-approved and active; expired certificates fail health checks.

## Upgrade and recovery

```bash
export CHAINCODE_VERSION=1.1
export CHAINCODE_SEQUENCE=2
bash scripts/fabric-deploy.sh
```

The wrapper is for the development network only. In production, package/install on each peer, query installed package IDs, obtain approvals from both MSPs for the same version/sequence/policy/collection configuration, run `peer lifecycle chaincode checkcommitreadiness`, commit the definition and query the committed definition. Never change endorsement or collection policy without organization agreement. Back up CA databases/MSP keys and peer block stores before upgrades; test a clean peer rebuild against the ordering service.

Ledger identity revocation immediately blocks application and chaincode authority. The worker then requests CA revocation and reports `ca_revoked`/`crl_update_required` on the operation. Publish newly generated CRLs in each affected channel MSP configuration using the organization-approved config-update/signature process. CA revocation by itself does not automatically update an already-created channel MSP. Expired/failed registrar authorization leaves a visible pending CA action and never undoes terminal ledger revocation.

An HA production Fabric deployment (multiple peers and at least three independently managed Raft consenters), channel MSP/CRL administration, external TLS/KMS/CA services and restoration tests remain operator prerequisites. These were not run in this Docker-free delivery environment.

## Bridge configuration reference

`BRIDGE_TOKEN` is the internal service secret (mapped from AEGIS_FABRIC_TOKEN in Compose); `BRIDGE_TLS_CERT`/`BRIDGE_TLS_KEY` select the HTTPS server material; `WALLET_DIR` and `WALLET_KEY` select encrypted persistent custody. `FABRIC_ORGANIZATIONS_FILE` is a trusted JSON configuration mount; `FABRIC_EVENT_IDENTITY` selects the active reader. Optional `PORT` defaults to 8443, and `FABRIC_CHANNEL`/`FABRIC_CHAINCODE` default to aegis. These are server configuration, never request-selected endpoints.

Each organization entry has `peer` (host:port), `peerHost` (expected TLS SAN), `tlsRoot` (peer TLS root file), `caUrl` (HTTPS endpoint), `caName`, `caTlsRoot` and `registrarMsp` (restricted client MSP for revocation). Use the exact container paths in organizations.example.json or override them consistently. Generated CRLs are retained at `/wallet/crls/<MSP>.pem`; publish them through channel governance. Revoke superseded enrollment identities according to registrar policy as well as the currently active ledger identity.
